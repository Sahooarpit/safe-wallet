# Safe Wallet: GNN Wash Trading Detector

An end-to-end Graph Neural Network (GNN) pipeline designed to detect Sybil attacks and wash trading rings on the Ethereum blockchain. By treating crypto wallets as nodes and transactions as edges, this system leverages **PyTorch Geometric (GraphSAGE)** to evaluate the behavior of wallet clusters rather than analyzing addresses in isolation.

## Project Overview

Wash trading and fraud networks often use a web of intermediary wallets to disguise their activity. Standard machine learning models that look at single-wallet statistics struggle to catch this because they lack context of the broader network topology. 

This project solves that by using a **GraphSAGE architecture (SAGEConv)**. 
- **Nodes** represent unique Ethereum wallets.
- **Edges** represent transactions connecting a sender to a receiver.
- **The Model** learns not only from a wallet's own transaction metrics but also aggregates the features of its counterparties (evaluating the graph up to 3 "hops" away). 

The repository includes:
1. **Training Pipeline:** Builds a graph from historical datasets and trains the GNN using a CrossEntropy/NLLLoss optimizer.
2. **Live Etherscan Pipeline:** An automated monitoring script that pulls live transaction histories from the Etherscan V2 API, builds subgraphs on the fly, engineers complex time-series features (like 5-minute burst counts and counterparty diversity), and evaluates risk scores in real-time.

---

## How It Classifies Risky vs. Safe Wallets

During live inference (etherscan_pipeline.py), the model evaluates the topological subgraph of a target address and outputs a logit distribution. We pass these raw scores through a Softmax function (calibrated using Temperature Scaling) to convert them into readable probabilities.

- **[HIGH RISK] (>50% Probability):** The wallet exhibits topological and statistical behavior highly correlated with wash trading. This typically includes a high mean_burst_5m (firing off many transactions in tight temporal windows), low mean_counterparty_div (transacting with the exact same tiny cluster of wallets repeatedly), and highly abnormal 
otional_zscores.
- **[CLEAN] (<50% Probability):** The wallet behaves like a normal network participant, transacting with a healthy diversity of counterparties at organic intervals and standard gas/notional distributions.

## How to Train & Evaluate

### 1. Training the Model
To build the dataset, engineer the graph features, and train the model, run:
`ash
python main.py --train
`
**What happens during training?**
* **Graph Building (data_processor.py):** Loads the tabular dataset, maps addresses to Node IDs, and connects them via edges. Calculates aggregated structural features (e.g., transaction degree, notional volume, gas averages).
* **Model Training (	rain_model.py):** Passes the massive, single-batch graph through the GNN. It optimizes weights using Negative Log-Likelihood Loss (NLLLoss).
* **Evaluation:** Uses **Macro F1 Score** to evaluate performance, preventing the massively imbalanced "Normal" class from overshadowing the rare "Wash Trader" class.
* **Artifacts:** Exports wash_trade_model.pth (model weights) and eature_scaler.pkl (feature standardizer) for live inference.

### 2. Live Etherscan Evaluation
To run inference on live Ethereum data, use the Etherscan pipeline. You can target a specific wallet:
`ash
python etherscan_pipeline.py --address 0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045
`
Or run it continuously without an address to automatically sample and scan the newest active wallets on the blockchain:
`ash
python etherscan_pipeline.py
`
This script paginates up to 10,000 recent transactions, builds the network graph, applies the scaler, and runs the subgraph through the trained model.

## Limitations & Ongoing Engineering Challenges

Building an enterprise-grade ML pipeline on live blockchain data presents severe challenges, primarily regarding data availability and model calibration.

### 1. The "Real Data" Bottleneck (Unavailability of Labeled Ledger Data)
* **Limitation:** Genuine, verified labels mapping actual wash-trading rings on Ethereum are incredibly scarce and highly proprietary (typically hoarded by analytics firms like Chainalysis). Open-source datasets (like those from Kaggle) are often completely synthetic, generated by basic heuristics, or aggregated in ways that strip out the actual wallet addresses.
* **The Problem:** A Graph Neural Network *strictly requires* topological data (who transacted with whom). We cannot use many high-quality NFT wash trading datasets because they only offer pre-computed row metrics (seller_24h_trade_count) without providing the raw transaction hashes and counterparties needed to build the edge_index.
* **Solution / Next Steps:** To truly make this model production-ready, we need to create a feedback loop: use the current GNN to flag highly suspicious networks on live Etherscan data, manually verify them via block explorers, and incrementally build our own proprietary, real-world labeled graph to retrain the model.

### 2. Etherscan API V1 Deprecation
* **Problem:** The popular etherscan-python package we used for querying the blockchain internally relies on Etherscan's V1 API (pi.etherscan.io/api), which was recently blocked, breaking the application.
* **Solution:** We injected a monkey-patch into etherscan_pipeline.py to intercept the package's internal URL generation and reroute all requests to the supported V2 API endpoint (/v2/api?chainid=1).

### 3. Strict API Rate Limits & Pagination Limits
* **Problem:** A standard Etherscan query maxes out at 1,000 records. Furthermore, continuous looping caused us to hit the 5 calls/second free-tier rate limit, crashing the pipeline.
* **Solution:** We swapped to a paginated fetching method (get_normal_txs_by_address_paginated) to pull up to 10,000 transactions, ensuring the GraphSAGE model has a large enough network to traverse. We also introduced a strict 	ime.sleep loop throttle to comfortably sit under the rate limit.

### 4. Overconfidence & Network Calibration
* **Problem:** Because the original Kaggle dataset was easy for the network to mathematically separate, the GNN achieved a 99% F1 score, leading to massive internal weights. When running inference on live data, this resulted in extreme "overconfidence" (predicting either exactly 100.0% or 0.0% with no nuance).
* **Solution:** We implemented **Temperature Scaling** in the etherscan_pipeline.py inference block. By mathematically softening the raw logits before they pass through the Softmax layer, the pipeline now provides highly calibrated, human-readable risk percentages.
